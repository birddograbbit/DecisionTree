# v0.2 Roadmap – Decision‑Tree‑Trading Platform

## 1  Purpose & Scope

Version 0.2 targets the **quality gap** revealed by the first ensemble release (v0.1).  The goal is to lift model skill, tighten risk, and align live‑trading readiness with the success metrics defined in the main project doc.

## 2  Problems Identified in v0.1

| #  | Area                           | Symptom                                                   | Root‑cause hypothesis                                             |
| -- | ------------------------------ | --------------------------------------------------------- | ----------------------------------------------------------------- |
| 1  | **Model skill**                | CV accuracy ≈ 0.52—coin‑flip                              | Limited/lagging features, unbalanced target, generic hyper‑params |
| 2  | **Risk‑adjusted return**       | Max Sharpe 0.33, CAGR/DD 0.28                             | Vol spikes, fixed 1 × sizing, no cost/slippage modelling          |
| 3  | **Drawdown control**           | DT & RegimeRF drawdown > 32 % (target < 25 %)             | Aggressive hold‑times, lack of stop‑loss / vol scaling            |
| 4  | **Trade dispersion**           | RF 4 trades vs XGB 73                                     | Per‑model prob thresholds and poor calibration                    |
| 5  | **Stacking under‑performance** | 1 trade, warnings about `lbfgs` convergence               | No scaling, too‑strict meta threshold, low `max_iter`             |
| 6  | **Convergence warnings**       | LogisticRegression hit iter‑limit                         | Features un‑scaled, default `max_iter` too low                    |
| 7  | **Probability calibration**    | DT outputs {0,0.527} only                                 | Needs `CalibratedClassifierCV` or isotonic                        |
| 8  | **Look‑ahead leakage risk**    | Preprocessors not pipelined                               | Fit/transform split not enforced                                  |
| 9  | **Missing costs**              | Back‑tests cost‑free                                      | Over‑optimistic metrics                                           |
| 10 | **Diagnostics**                | Sparse visibility into rolling performance & regime stats | Need interactive dashboard                                        |
| 11 | **RegimeAdaptiveStrategy**     | `backtest_engine` attribute errors & date ambiguity       | Missing initialization and pandas index/column conflicts          |

## 3  Objectives for v0.2

* Raise **time‑series CV accuracy** to **≥ 57 %**.
* Achieve **Sharpe ≥ 0.7** and **CAGR/Max DD ≥ 0.35** in cost‑inclusive back‑tests.
* Cap strategy **Max Drawdown at 25 %**.
* Establish an **automated hyper‑parameter search** framework.
* Provide an **interactive dashboard** for model diagnostics and live PnL.

## 8 Progress Report: Phase 1.5 — Hyperparameter Optimization Integration

### Problem: RegimeAdaptiveStrategy Execution Failures

During testing of the regime-specific hyperparameter optimization functionality, we encountered critical errors in the RegimeAdaptiveStrategy class that were blocking further progress:

1. **Missing `backtest_engine` attribute**: The strategy attempted to access a `backtest_engine` attribute that was never initialized, resulting in:
   ```
   AttributeError: 'RegimeAdaptiveStrategy' object has no attribute 'backtest_engine'
   ```

2. **Date column ambiguity**: The signals DataFrame had 'date' both as an index and column name, causing pandas operations to fail:
   ```
   ValueError: 'date' is both an index level and a column label, which is ambiguous
   ```

3. **Boolean index length mismatch**: There's an additional issue with Boolean indexing that's causing errors:
   ```
   Boolean index has wrong length: 4412 instead of 4343
   ```

### Solutions Implemented

To address these issues, we've implemented several fixes in PR #78:

#### 1. Permanent Fix (Main Implementation)
- Added proper initialization of `backtest_engine` in the `initialize` method 
- Applied systematic checks for date ambiguity throughout the code
- Enhanced error handling in critical methods
- Created a comprehensive solution that avoids redundant code paths

#### 2. Alternative/Temporary Solutions
- **Patch Script (`fixed_regime_strategy.py`)**: A non-invasive patch that monkey-patches key methods 
- **Wrapper Script (`run_fixed_strategy.py`)**: A simple interface for running strategies with the fixes applied

### Next Steps for Phase 1.5

With the fixed RegimeAdaptiveStrategy, we can now proceed with the remaining hyperparameter optimization tasks:

1. **O-4: Regime-specific hyperparameter optimization**
   - Now unblocked after PR #78 is merged
   - Requires resolving the remaining Boolean indexing issue (Issue #79)
   - Implementation plan: create separate hyperparameter sets for each market regime

2. **O-5: Adaptive probability thresholds**
